Agent Protocol DSL: A Declarative Protocol for Runtime-Orchestrated LLM Agents

A position-and-system draft for replacing imperative tool-call loops with model-generated, runtime-validated agent protocols.

Abstract

Large language model agents are commonly implemented through imperative tool-call loops: the model repeatedly selects a tool, observes the result, and decides the next action. This pattern works well for short interactions, but it forces the model to act simultaneously as planner, dispatcher, state manager, observation filter, and user-facing narrator. As tasks become longer and tool outputs become larger, the loop can introduce excessive context noise, unnecessary model turns, poor parallelism, and limited transparency for users.

We propose Agent Protocol DSL, a declarative agent protocol in which the model emits a JSON + Markdown execution specification rather than issuing step-by-step native tool calls. The specification describes an action graph, executors, capabilities, result policies, permission policies, user-visible notes, and references. A runtime parses, validates, schedules, and executes the protocol. Instead of replaying full tool outputs into the model context, the runtime renders compact structured Markdown observation turns that describe what was executed, what was found, what failed, and where full artifacts are stored.

The key idea is an asymmetric bidirectional protocol: model-to-runtime communication uses an expressive declarative DSL, while runtime-to-model communication uses a compressed observation format optimized for context efficiency. We evaluate the approach against imperative tool-call baselines on software engineering and information gathering tasks, measuring token usage, model turns, latency, task success, error recovery, context pollution, and user-rated transparency.

1. Motivation

Current agent systems often treat tool use as a conversational loop. The model decides one action, the runtime executes it, the result is returned to the model, and the model decides again. This imperative pattern is simple and flexible, but it has a structural weakness: every intermediate step must pass through the model context.

For complex tasks, this creates four problems.

First, context pollution. Tool outputs are often much larger than the information actually needed for the next decision. A test run may produce thousands of tokens, while the model only needs the failing test names and a reference to the full log.

Second, excessive model turns. If a task requires ten actions, an imperative loop may require ten or more model calls, even when several actions are independent and could run in parallel.

Third, weak runtime optimization. Because the model decides one step at a time, the runtime has limited access to the whole task structure. It cannot easily optimize scheduling, dependency execution, result reduction, permission gating, or artifact management.

Fourth, poor user transparency. A raw tool-call trace is not the same as a user-understandable task view. Users need to know what the agent is doing, which permissions are being requested, what progress has been made, and where results came from.

Agent Protocol DSL addresses these issues by replacing imperative tool-call orchestration with a declarative protocol. The model declares an executable task graph. The runtime validates and executes it. The model receives only reduced observations and references.

The analogy is similar to SQL, but not identical. SQL does not tell a database engine how to scan, join, and optimize step by step; it declares the desired relation. Agent Protocol DSL does not ask the model to drive every tool invocation step by step; it declares an executable task graph that the runtime can validate, schedule, execute, reduce, and project to the user.

2. Declarative Agent Protocols

We distinguish two orchestration models.

Imperative tool-call orchestration asks the model to repeatedly answer: what tool should be called next, with which arguments, after seeing the previous result?

Declarative protocol orchestration asks the model to specify: what task graph should be executed, with which dependencies, capabilities, permissions, result policies, user-visible notes, and references?

The difference is not merely syntactic. It changes where responsibility lives. In tool-call loops, the model is planner, dispatcher, and observation manager. In Agent Protocol DSL, the model remains the planner, but the runtime becomes the dispatcher, validator, scheduler, reducer, permission checker, artifact manager, and user projection engine.

Dimension Imperative Tool-Call Loop Declarative Agent Protocol DSL
Basic unit Single tool call Action graph / task specification
Control flow Model decides step by step Model declares, runtime schedules
Observation Tool result is usually replayed Policy-reduced structured Markdown observation
Parallelism Discovered dynamically or by framework Explicit DAG dependencies
Permissions Handled outside the call loop Protocol-level permission policy
User visibility Chat trace or tool trace User-facing task projection

3. System Design

Agent Protocol DSL uses an asymmetric bidirectional protocol. The model emits a JSON + Markdown DSL. JSON expresses machine-checkable execution structure. Markdown expresses user-visible notes, natural-language instructions, and references.

Runtime-to-model feedback is rendered as structured Markdown observation turns. The runtime keeps machine-readable JSON records internally for artifacts, metrics, UI rendering, and evaluation, but the model-visible observation is optimized for semantic reasoning rather than programmatic parsing.

3.0 Model Interface Modes

Agent Protocol DSL does not assume that the model supports native tool calling. The primary interface is ordinary text: the runtime sends ordered model-readable turns, the model replies with one fenced json agent-protocol block and optional Markdown sections, and the runtime parses and validates that text before execution.

Native tool calling can be used by an adapter to constrain or transport the interaction, but it is not the protocol boundary. This makes the protocol portable across models that expose different tool-call APIs, or no tool-call API at all. The essential contract is that the model declares an executable protocol object; it does not directly invoke provider-native tools. 

```json agent-protocol
{
  "type": "agent.protocol.output",
  "version": "1",
  "intent": "execute",
  "payload": {
    "type": "action_graph",
    "actions": []
  }
}
```

3.1 Model-to-Runtime DSL

A protocol instance contains an action graph, executors, capabilities, result policy, permission policy, user-visible note, and references.

{
  "graph": [
    {
      "id": "scan",
      "executor": "repo.search",
      "capabilities": ["read"],
      "result_policy": "summary+refs"
    },
    {
      "id": "test",
      "executor": "repo.test",
      "depends_on": ["scan"],
      "capabilities": ["execute"],
      "result_policy": "failures+refs"
    }
  ],
  "user_note": "I will inspect relevant files and run focused tests.",
  "references": []
}

3.2 Runtime-to-Model Observation

The runtime does not replay complete tool outputs by default. It returns a structured Markdown observation turn: 

<turn index="3" role="runtime">
Execution status: partially failed.

Actions and results:
1. Action: Run focused session refresh tests.
   Result: The test command failed.
   Failure reason: 2 tests failed in session refresh behavior.
   Evidence: artifact://test/stdout

Note:
The full test output was not replayed into the model context.

Next:
Decide whether to inspect the implementation and repair the failure.
</turn>

We define a summary as the minimal decision-relevant projection of an execution result, generated according to a declared result policy and backed by artifact references.

4. Relation to Existing Work

ReAct and tool-call loops use an imperative interaction pattern. The model alternates between reasoning, action, and observation. Agent Protocol DSL instead asks the model to declare a task graph and lets the runtime execute it.

Native tool calling from major model providers improves local tool invocation. Models are trained to select tools and produce valid arguments. However, this training mainly helps individual tool calls. It does not solve task-level orchestration, context reduction, artifact management, permission policy, or user projection.

Anthropic Programmatic Tool Calling also addresses round-trip and context overhead by letting models write code that orchestrates tools. Agent Protocol DSL takes a different path: instead of asking the model to generate executable code, it asks the model to generate a declarative protocol that can be validated and constrained by the runtime.

ReWOO and LLMCompiler show that separating planning from observation and enabling parallel tool execution can improve efficiency. Agent Protocol DSL extends this direction into a broader protocol design that includes permissions, result policies, artifact references, and user-visible projection.

LangGraph and AutoGen provide graph-based and multi-agent orchestration frameworks, but their graphs are typically defined by developers in program code or UI configuration. Agent Protocol DSL makes the graph a model-generated protocol object.

MCP standardizes how tools and resources are exposed to agents. Agent Protocol DSL targets a different layer: how the model specifies a task for runtime execution and how the runtime reports reduced observations back to the model.

5. Research Questions

  1. Context Efficiency. Does Agent Protocol DSL reduce token usage, model turns, and irrelevant observation tokens compared with imperative tool-call loops?
  2. Execution Effectiveness. Does declarative runtime orchestration improve or preserve task success rate while reducing latency on multi-step agent tasks?
  3. Transparency and Control. Does user projection improve users' understanding of agent progress, permissions, and result provenance?
  4. Model Compatibility. Can general-purpose LLMs generate valid and effective Agent Protocol DSL without protocol-specific fine-tuning?

6. Evaluation Plan

We compare three systems.

  • Baseline A: Native tool-call loop. The model invokes tools step by step. Full or standard tool outputs are returned to context.
  • Baseline B: Tool-call loop with compressed Markdown observations. The orchestration remains imperative, but tool outputs are compressed into structured Markdown observations. This isolates the effect of result compression from the effect of declarative planning.
  • System C: Agent Protocol DSL. The model emits a declarative action graph. The runtime validates, schedules, executes, stores artifacts, and returns structured Markdown observation turns.

Metrics include total token usage, model turns, end-to-end latency, task success rate, error recovery quality, invalid protocol rate, repair attempts per task, user-rated transparency, and context pollution.

Task categories include coding agent tasks, code review tasks, multi-file edit tasks, test generation tasks, information gathering tasks, and multi-agent delegation tasks.

7. Ablations

  • No result policy
  • No user projection
  • No executor auto selection
  • No Markdown references
  • Sequential-only execution instead of DAG execution
  • Full result replay instead of summary/ref replay
  • No schema validation repair
  • No permission policy

The most important ablations are full result replay versus summary/ref replay, and user projection versus raw trace. These directly test the central claims of context efficiency and transparency.

8. Expected Claims

We expect the strongest claims to be conditional, not universal.

Agent Protocol DSL is expected to reduce model turns, token usage, and context pollution on tasks with multiple actions or large intermediate outputs. DAG execution is expected to reduce latency when actions can run independently. Policy-governed result reduction is expected to preserve task success while reducing irrelevant observation tokens. User projection is expected to improve user understanding of task state, permissions, and result provenance.

The protocol may not outperform native tool calling on simple one-step tasks. In such cases, DSL overhead may dominate.

9. Risks and Limitations

  • The protocol depends on the model's ability to generate valid structured specifications.
  • The DSL may introduce overhead for simple tasks.
  • Summaries may omit information needed for later reasoning.
  • LLM-assisted summarization can hallucinate or distort long outputs.
  • The system improves permission visibility but does not solve agent security.
  • Evaluation results may depend heavily on runtime implementation quality.

10. Model Training and Compatibility

A major question is whether a protocol not explicitly targeted by provider-side tool-call training can work reliably. Our hypothesis is yes, because the protocol is built from capabilities that current LLMs already possess: structured JSON generation, Markdown writing, task decomposition, dependency expression, and instruction following.

Tool-call-tuned models have an advantage on individual tool selection and argument generation. Agent Protocol DSL targets a different level: task-level orchestration and observation management.

The protocol should be usable in a zero-shot or few-shot setting with schema validation and repair. Constrained decoding can further improve JSON validity. Fine-tuning is not required for the first prototype, but the protocol provides a stable target for future post-training.

This compatibility claim should be evaluated in a text-only setting as well as with tool-call-capable models. In the text-only setting, the model receives the protocol schema and examples in ordinary prompt text and must emit a fenced protocol block. The runtime then measures valid DSL rate, repair attempts, executor selection accuracy, and task success.

11. Submission Strategy

The recommended path is staged. First, publish an arXiv preprint with the protocol, runtime architecture, examples, and pilot evaluation. Second, submit to an ICLR or NeurIPS workshop on agents, tool use, or foundation model systems. Third, choose the full-paper venue based on the strongest evidence.

  • ASE / FSE / ICSE if the strongest results are coding-agent benchmarks.
  • CHI / UIST if the strongest results are user projection and human-agent interaction.
  • ACL / EMNLP System Demo if the strongest artifact is an interactive system demo.

The most natural full-paper framing is software engineering agents: a declarative protocol and runtime architecture for context-efficient, auditable software engineering agents.

12. Conclusion

Agent Protocol DSL reframes agent execution as a declarative protocol rather than an imperative tool-call loop. The model specifies what should be executed; the runtime decides how to validate, schedule, execute, reduce, store, and project the task.

The central contribution is not a new tool API. It is a separation of responsibilities: model as planner, runtime as executor and reducer, user interface as projection layer. By combining JSON + Markdown task specifications with structured Markdown observations, the system creates an asymmetric protocol optimized for both expressiveness and model-readable context efficiency.
