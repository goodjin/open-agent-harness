# Workflow Durable Orchestration Adapter

## Purpose

Workflow is the first durable orchestration adapter on top of the Harness governance protocol.

It is not the whole Harness protocol and should not try to predefine every possible agent workflow. It defines the structure, constraints, state files, and result protocol that let an orchestrator agent generate a task-specific durable run and let the runtime execute, resume, audit, and repair it.

The adapter must obey the governance model in `docs/harness-protocol/00-harness-governance-protocol.md`: Runtime owns validation, state transitions, scheduling, permissions, events, projections, and gates. Workflow-specific files are adapter state under the broader Harness run model.

The same format must support both:

- dynamic workflows generated by a Planner / Orchestrator agent
- static workflows written by humans for repeatable procedures

## Design Principles

- The workflow DSL describes orchestration state, not provider scheduling limits.
- The workflow file is a run record, not only a reusable template.
- The runtime owns validation, state transitions, scheduling, and permissions.
- The Planner owns workflow generation and later decision-making when execution cannot proceed deterministically.
- Workers own node execution only.
- Static and generated workflows must converge to the same durable run layout before execution.
- Every state change that matters for resume must be persisted before the next action starts.

## Terminology

- **Template**: a reusable workflow definition from package or user config.
- **Run**: a materialized workflow instance under `.opencode/harness/runs/<run>/workflow/`.
- **Workflow file**: the `workflow.json` run manifest and DAG.
- **Node file**: the durable assignment, progress, result, and error record for one DAG node.
- **Artifact**: any larger output referenced by path instead of embedded in JSON.
- **Decision**: a structured response from Planner / Decision Agent after a failure, block, or replan request.

## When To Generate A Workflow

Agents should not generate workflow DSL by default. Workflow generation is reserved for orchestration entrypoints.

Generate a workflow when at least one condition is true:

- the task has multiple dependent stages
- the task has independent subtasks that can run in parallel
- execution needs multiple agents or new sessions
- execution must survive process restart or session interruption
- failure handling needs retry, cancellation, added nodes, or replanning
- the user explicitly asks for orchestration, a long-running task, a plan that should execute, or progress tracking

Do not generate a workflow for:

- single-turn answers
- simple code explanations
- small single-session edits
- a single command
- worker execution of an already assigned node

Worker agents do not create workflows. They execute one assigned node and update that node's state file. If a worker cannot complete the node, it reports a structured status such as `blocked`, `failed`, or `needs_replan`.

## Roles

### Planner / Orchestrator

The Planner is allowed to create the initial workflow and persist it before execution starts. It defines the DAG, node goals, dependencies, node types, success criteria, input references, and failure policies.

### Worker

The Worker executes exactly one node assignment. It reads the node file and referenced inputs, performs the task, writes progress, and finishes with a structured result.

The Worker should not know the full workflow generation rules. It only needs the node state protocol.

### Decision Agent

The Decision Agent handles exceptional execution states. In the first implementation, this can be the same agent as Planner. The runtime should still treat it as a separate role so a future Recovery agent can replace it without changing the workflow DSL.

The Decision Agent may choose one of a bounded set of actions:

- `retry_node`
- `skip_node`
- `cancel_branch`
- `add_node`
- `modify_node`
- `request_input`
- `replan_workflow`
- `abort_workflow`

## Workflow Runner Agent Contract

Workflow Runner is the adapter-specific agent role that understands and creates durable workflow run records. It can be primary and delegable, but should not be the default general coding agent unless the product explicitly wants workflow-first orchestration behavior.

Recommended template:

```json
{
  "id": "workflow-runner",
  "name": "Workflow Runner",
  "role": "You are the Workflow Runner. You convert complex goals into durable workflow DAG runs, coordinate execution through the runtime, and make bounded decisions when execution is blocked.",
  "description": "Primary orchestration agent for durable workflow DAG generation, execution coordination, and recovery decisions.",
  "entry": {
    "primary": true,
    "delegable": true,
    "mentionable": true,
    "default": false,
    "hidden": false
  },
  "capability": {
    "purpose": "workflow_orchestration",
    "tags": ["workflow", "orchestration", "planning", "decision"],
    "cost": "high",
    "writes": true
  },
  "workflow_mode": "supervision",
  "permission_mode": "custom"
}
```

Workflow Runner owns:

- deciding whether the request needs workflow mode
- generating the smallest useful workflow DAG
- defining global goal, assumptions, success criteria, node tasks, dependencies, input refs, and failure policy
- using `workflow.create`, `workflow.start`, `workflow.status`, `workflow.decide`, and `workflow.abort`
- acting as the first Decision Agent for blocked, failed, or `needs_replan` states
- updating run structure only through runtime-validated decisions

Workflow Runner does not own:

- executing worker nodes directly unless assigned by runtime
- mutating worker-owned node progress
- bypassing schema, permission, gate, or state-machine validation
- encoding provider/model concurrency in workflow DSL
- inventing unrelated workflow syntax during task execution

Workflow Runner prompt rules:

- Generate workflow DSL only for complex, multi-stage, parallel, multi-agent, resumable, or failure-sensitive tasks.
- Do not generate workflow DSL for simple answers, small single-session edits, single commands, or delegated worker nodes.
- Treat the workflow DSL as a durable DAG DSL, not a general-purpose programming language.
- Persist `workflow.json` and initial node files before execution starts.
- Keep the initial DAG small and add nodes later only through validated decisions.
- Use node types as routing hints, not fixed agent ids.
- Do not execute worker nodes yourself unless the runtime explicitly assigns the node to this agent.
- When execution fails or blocks, choose one bounded decision action and explain the reason.

Recommended node type routing:

| Node type | Desired capability |
|---|---|
| `research` | source reading, docs, code search |
| `design` | architecture, API design, planning |
| `implementation` | code editing and focused implementation |
| `test` | command execution, test diagnosis |
| `review` | code review, correctness, regression risk |
| `gate` | deterministic validation, release or merge checks |
| `summary` | final synthesis and user-facing report |

Workflow Runner may request an agent, but runtime must resolve and validate it against `entry.delegable`, `capability`, authority, and permission policy.

## Runtime Responsibilities

The runtime is the enforcement layer. Agent rules are guidance; runtime checks are mandatory.

The runtime must:

- validate workflow files before execution
- persist workflow files before scheduling any node
- persist every node state transition
- schedule runnable DAG nodes based on dependencies
- decide actual parallelism from provider, model, and agent pool limits
- route nodes to suitable agents from node type and capability metadata
- restrict workers to updating their assigned node files
- restrict workflow mutation to Planner / Decision roles
- use atomic writes for state files
- append state changes to an event log when possible

Concurrency is not part of the workflow DSL. The DAG exposes which nodes may run together; the scheduler decides how many actually run.

## Loop Nodes

The outer workflow graph remains a DAG. Feedback cycles such as test-fix-retest, draft-review-revise, generate-evaluate-retry, and reproduce-fix-verify are represented as a `loop` node, not as an edge back to an earlier DAG node.

A `loop` node is a composite node that repeats child steps inside the node boundary. The node id is task-specific and generated by the planner; names such as `validate`, `stabilize`, or `qa` are examples, not reserved DSL concepts.

Initial feature development usually belongs in a standard outer DAG node. Repair, revision, or retry work caused by feedback belongs inside the loop node. This keeps the global dependency graph analyzable while still allowing bounded runtime feedback.

Loop node shape:

```json
{
  "id": "feedback_loop",
  "type": "loop",
  "depends_on": ["implement"],
  "loop": {
    "max_attempts": 5,
    "until": [{ "type": "variable", "name": "feedback_loop.test", "equals": "passed" }],
    "memory": {
      "include": ["node.goal", "attempts.summary", "steps.test.output", "artifacts.diff"],
      "summarize": { "when": "context_tokens > 24000" }
    },
    "steps": [
      {
        "id": "test",
        "type": "test",
        "session": "per_call",
        "prompt": "Run validation. Return exactly `passed` when it succeeds; otherwise return failure details."
      },
      {
        "id": "fix",
        "type": "debug",
        "session": "per_loop",
        "mutates": true,
        "context": { "include": ["steps.test.output", "attempts.previous.fix", "artifacts.diff"] },
        "prompt": "Fix the reported failures and summarize changed files."
      }
    ]
  }
}
```

Runtime semantics:

- each loop execution creates attempt records under the parent run context
- child step run keys are scoped as `parent.child`, such as `feedback_loop.test`
- `until` is evaluated against the parent run context after child steps update variables
- `max_attempts` is a hard safety limit
- child agents run in separate sessions with their own role prompts
- runtime builds scoped context snapshots from structured workflow state and artifacts; it should not blindly copy the full parent conversation
- `per_call` creates a fresh child session for each call
- `per_loop` reuses the same child session for that child step within the loop node when possible

The parent run context is the source of truth. Child agent sessions receive selected state, execute one child step, and return results that are merged back into the parent context.

## Workflow Tool Contract

Workflow generation must use a runtime-owned tool protocol.

The Planner / Workflow Runner does not create workflow files by free-form text and does not execute workflow steps by itself. It calls a runtime-owned tool with a structured workflow definition. The runtime validates, persists, schedules, resumes, and reports progress.

Initial tool surface:

- `workflow.create`: submit a workflow DAG definition for the active user request
- `workflow.start`: start a previously created workflow run
- `workflow.status`: read the current workflow run and node status
- `workflow.decide`: submit a bounded recovery decision when execution is blocked
- `workflow.abort`: cancel a workflow run

`workflow.create` should:

- accept only the workflow adapter schema
- validate the schema before any execution starts
- assign or validate a unique workflow id
- persist the workflow definition before scheduling any node
- create or reference per-node state records
- return a structured status containing workflow id, run id, status, validation result, and next action
- default to `status: "created"` or `status: "ready"`, not execution

`workflow.start` should:

- accept a `run_id` created by `workflow.create`
- start scheduling only after the workflow has been persisted and validated
- return a model-visible structured execution result
- include workflow id, run id, status, completed nodes, active nodes, failed nodes, outputs, artifacts, and any pause/error reason

The tool result returned by `workflow.start` is the handoff back to the model. The model should use that result to produce the final user-facing response or to request a bounded decision if the workflow paused or failed.

The model-facing contract is therefore:

- decide whether workflow mode is warranted
- if warranted, call `workflow.create` exactly once with the workflow DAG
- call `workflow.start` after `workflow.create` succeeds only when the user asked to execute the work
- do not call `workflow.start` when the user only asked to design, plan, preview, or save a workflow
- do not output workflow JSON as assistant prose
- do not call read/edit/bash/task tools to execute workflow steps before the workflow runtime assigns execution
- after `workflow.start` returns, read the tool result and summarize the execution outcome for the user
- if not warranted, proceed with normal chat/tool behavior

The program-facing contract is:

- recognize workflow creation from the tool call, not from assistant text parsing
- treat the tool call result as the source of truth for persistence and execution
- drive the execution loop after `workflow.start`
- return terminal, paused, or failed workflow execution status to the model as tool output
- expose progress to the UI from runtime state, not from model-written summaries

## Planner Generation Contract

When a Planner generates a workflow, it must:

- decide that workflow mode is warranted using the generation criteria above
- call `workflow.create` with the workflow definition
- let the runtime create the unique run directory or durable run record
- let the runtime write `workflow.json` and per-node state records
- let the runtime validate DAG ids, dependency references, cycles, and node types
- wait for the tool result before assuming the workflow exists
- call `workflow.start` only when execution should begin immediately

The Planner must include enough intent for later recovery:

- global goal
- assumptions
- success criteria
- per-node goal and task
- per-node success criteria
- dependency rationale when it is not obvious
- failure policy

The Planner should keep the first DAG as small as practical. It should not pre-expand speculative recovery branches. Failed or missing work can be added later through a Decision action.

## Worker Execution Contract

When a Worker receives a node assignment, it must:

- read the assigned node file
- read only referenced upstream node files and artifacts unless the task requires more context
- update progress in the assigned node file
- write artifacts under the workflow run `artifacts/` directory
- finish with one terminal node status or a decision-request status

The Worker must not:

- create a new workflow
- edit `workflow.json`
- edit another node's file
- change DAG dependencies
- silently continue after a blocker that invalidates the node goal

If the Worker believes the plan is wrong or incomplete, it should mark the node `needs_replan` and explain why in `error` or `signals`.

## Persistent Layout

Use a fixed workflow root, but never a fixed workflow instance directory. Every workflow run gets a unique directory.

Recommended project-local layout:

```txt
.opencode/harness/runs/
  run_20260517_103012_a8f3/
    workflow/
      workflow.json
      lock
      events.jsonl
      nodes/
        research.json
        design.json
        implement.json
        test.json
      artifacts/
        research.md
        patch.diff
      decisions/
        failure_001.json
```

The run id should include a timestamp and random suffix to avoid collisions across sessions:

```txt
run_YYYYMMDD_HHMMSS_<random>
```

Multiple sessions can safely create workflows under the same root as long as each workflow has its own directory. Concurrent updates to the same workflow must use a lock or atomic file writes.

## Workflow File

`workflow.json` is the stable DAG definition and run manifest. It should reference node files instead of embedding large progress or result payloads.

Recommended top-level fields:

| Field | Required | Owner | Notes |
|---|---:|---|---|
| `id` | yes | runtime | Unique workflow run id. |
| `schema` | yes | runtime | Integer schema version. |
| `goal` | yes | Planner | User-facing objective. |
| `status` | yes | runtime | Workflow status enum. |
| `created_at` | yes | runtime | ISO timestamp. |
| `updated_at` | yes | runtime | ISO timestamp. |
| `assumptions` | no | Planner | Planning assumptions useful for later decisions. |
| `success_criteria` | yes | Planner | Global completion criteria. |
| `nodes` | yes | Planner/runtime | DAG node references. |
| `policies` | no | Planner/runtime | Default failure and blocking behavior. |

```json
    {
      "id": "implement",
      "type": "implementation",

      "id": "test",

      "id": "review",

```

`workflow.json` should not contain provider concurrency settings.

Workflow node references should stay small:

| Field | Required | Notes |
|---|---:|---|
| `id` | yes | Stable node id unique within the workflow. |
| `type` | yes | Node type enum used for routing. |
| `title` | yes | Short display title. |
| `file` | yes | Relative path to the node file. |
| `depends_on` | yes | Node ids that must complete first. |
| `optional` | no | Whether downstream can proceed if this node is skipped. |

The runtime must reject duplicate ids, missing dependency targets, self-dependencies, and cycles.

## Node Types

Node type is a routing hint, not a hard-coded agent id. The runtime maps node type plus task content to an agent candidate using registry metadata.

Initial node type enum:

- `research`
- `planning`
- `design`
- `implementation`
- `debug`
- `test`
- `review`
- `gate`
- `documentation`
- `build`
- `release`
- `decision`
- `manual`

The mapping should be configurable. For example, `implementation` may route to a coding-capable agent, while `review` may route to a review agent. The workflow DSL should allow an optional requested agent, but the runtime should still resolve the final agent.

Routing should use this precedence:

1. explicit node `agent.requested`, if present and allowed
2. node type to capability mapping
3. agent registry `capability.tags` and `capability.purpose`
4. default delegable agent for the current model/provider

An agent is eligible only if its entry metadata allows delegation and its permission profile can satisfy the node's expected writes and tools.

## Verification And Gates

Implementation nodes should not silently absorb testing and review. The DSL should represent verification in two layers:

- node properties define required acceptance and verification gates
- dedicated `test`, `review`, or `gate` nodes execute those gates

This makes verification schedulable, retryable, auditable, and recoverable. It also lets the runtime distinguish:

- implementation completed but tests failed
- tests passed but review failed
- review passed but final gate needs a user or policy decision

Recommended pattern:

```txt
implement -> test -> review -> gate -> next
```

For broader changes:

```txt
             -> unit_test
implement -> typecheck -> review -> gate -> next
             -> integration_test
```

Implementation node example:

```json
{
  "id": "implement",
  "type": "implementation",
  "title": "Apply the code change",
  "file": "nodes/implement.json",
  "depends_on": ["research"],
  "verification": {
    "required": true,
    "strategy": "separate_nodes",
    "must_pass": ["test", "review"],
    "commands": ["bun typecheck"],
    "notes": [
      "Add or update focused tests for changed behavior.",
      "Do not mark implementation accepted until test and review nodes pass."
    ]
  }
}
```

Test node example:

```json
{
  "id": "test",
  "type": "test",
  "title": "Verify changed behavior",
  "file": "nodes/test.json",
  "depends_on": ["implement"],
  "success_criteria": [
    "Focused tests for changed behavior pass.",
    "Typecheck passes from the relevant package directory."
  ]
}
```

Review node example:

```json
{
  "id": "review",
  "type": "review",
  "title": "Review implementation and tests",
  "file": "nodes/review.json",
  "depends_on": ["test"],
  "success_criteria": [
    "Implementation satisfies the workflow goal.",
    "Tests cover the critical behavior and failure paths.",
    "No unrelated refactors or regressions are introduced."
  ]
}
```

Gate nodes are optional but useful when multiple verification branches must converge or when a user/policy decision is required before downstream work starts.

The runtime should treat `verification.must_pass` as an acceptance contract. A node with unmet required verification must not be considered accepted for workflow completion, even if its own execution status is `success`.

## Status Model

Workflow status:

- `created`
- `ready`
- `running`
- `success`
- `failed`
- `blocked`
- `cancelled`
- `needs_decision`
- `needs_replan`

Node status:

- `pending`
- `ready`
- `running`
- `success`
- `failed`
- `blocked`
- `skipped`
- `cancelled`
- `needs_decision`
- `needs_replan`

Only nodes whose dependencies have reached `success` or an allowed terminal state may become `ready`.

Allowed node transitions:

```txt
pending -> ready
ready -> running
running -> success
running -> failed
running -> blocked
running -> needs_decision
running -> needs_replan
failed -> ready
blocked -> ready
needs_decision -> ready
needs_replan -> ready
ready -> cancelled
pending -> cancelled
running -> cancelled
ready -> skipped
pending -> skipped
```

`failed`, `blocked`, `needs_decision`, and `needs_replan` are not always terminal. They pause scheduling for affected downstream nodes until deterministic policy or a Decision action resolves them.

Allowed workflow transitions:

```txt
created -> ready
ready -> running
running -> success
running -> failed
running -> blocked
running -> needs_decision
running -> needs_replan
running -> cancelled
needs_decision -> running
needs_replan -> running
blocked -> running
failed -> running
```

The runtime should reject stale transitions. For example, a Worker cannot write `success` after the runtime already cancelled the node.

## Failure Handling

The runtime should first apply deterministic policy:

- retry retryable errors within `max_attempts`
- skip nodes only when policy explicitly permits it
- cancel downstream nodes when a required dependency is cancelled or failed
- route failed `test`, `review`, or `gate` nodes to Decision Agent before accepting upstream implementation nodes
- block workflow completion while any required `verification.must_pass` node is not successful

When deterministic policy cannot decide, the runtime asks the Decision Agent. The Decision Agent reads:

- `workflow.json`
- the failed node file
- related upstream node files
- relevant artifacts
- `events.jsonl`

It then writes a decision file under `decisions/` and returns a bounded action. If the action changes the DAG, the runtime validates and persists the updated workflow before continuing.

Decision file example:

```json
{
  "id": "decision_001",
  "workflow_id": "wf_20260517_103012_a8f3",
  "node_id": "test",
  "created_at": "2026-05-17T10:42:00Z",
  "action": "add_node",
  "reason": "The test failed because generated SDK files were not refreshed after the implementation node.",
  "changes": {
    "nodes": [
      {
        "id": "regenerate_sdk",
        "type": "build",
        "title": "Regenerate JavaScript SDK",
        "file": "nodes/regenerate_sdk.json",
        "depends_on": ["implement"]
      }
    ],
    "replace_edges": [
      {
        "from": "implement",
        "to": "test",
        "with": ["regenerate_sdk", "test"]
      }
    ]
  }
}
```

Decision actions must be validated before mutation. Invalid decisions should leave the workflow paused in `needs_decision` with an error event.

## Event Log

`events.jsonl` is append-only. It is not the source of truth, but it makes debugging, audit, and replay easier.

Recommended event shape:

```json
{
  "time": "2026-05-17T10:35:00Z",
  "type": "node_status",
  "workflow_id": "wf_20260517_103012_a8f3",
  "node_id": "implement",
  "from": "ready",
  "to": "running",
  "actor": "runtime"
}
```

Useful event types:

- `workflow_created`
- `workflow_status`
- `node_created`
- `node_status`
- `node_progress`
- `artifact_written`
- `decision_requested`
- `decision_applied`
- `decision_rejected`
- `workflow_resumed`
- `workflow_cancelled`

## Persistence Rules

All JSON writes should use atomic replacement:

1. read current file
2. validate expected version or `updated_at`
3. write next content to a temporary file in the same directory
4. fsync when practical
5. rename over the target file
6. append an event

Each mutable file should include either a monotonically increasing `rev` or an `updated_at` timestamp that the writer checked before writing. `rev` is preferred for conflict detection.

Recommended ownership:

| File | Writers |
|---|---|
| `workflow.json` | runtime, Planner, Decision Agent through runtime validation |
| `nodes/<id>.json` | runtime and assigned Worker |
| `events.jsonl` | runtime |
| `decisions/*.json` | runtime after Decision Agent output validation |
| `artifacts/*` | assigned Worker or runtime |

Workers should submit node updates through runtime APIs when available. Direct file writes are acceptable only for early local implementation and must still obey ownership and atomic write rules.

## Resume Rules

On startup or resume, the runtime should:

1. discover workflow run directories
2. load and validate `workflow.json`
3. load every referenced node file
4. mark stale `running` nodes as `blocked` or `needs_decision` unless the owning session is still alive
5. recompute ready nodes from the DAG
6. continue scheduling only after all state files are consistent

If `workflow.json` references a missing node file, the workflow should enter `needs_decision`. If an unreferenced node file exists, the runtime should leave it untouched and record an audit event.

## Schema Boundaries

The workflow DSL should avoid becoming a programming language. Do not add arbitrary loops, general expressions, or unbounded code execution to workflow files.

Allowed control flow for the first DAG design:

- dependency edges
- optional nodes
- guard checks
- bounded retry policy
- Decision Agent mutations after runtime validation

Anything more complex should be represented by adding or modifying nodes through a Decision action, not by embedding a script language into the workflow DSL.

## Static Workflows

Static workflows should use the same schema. They can live under package or user config directories, but each run should still be copied or materialized into a unique durable run directory before execution.

Static definitions are templates. Runtime workflow directories are execution records.

## Adapter Target Shape

The workflow adapter target shape is:

- DAG `nodes` with explicit dependencies
- workflow definition separated from per-node durable state files
- routing by node type and agent capability
- scheduler-owned concurrency policy
- Planner / Workflow Runner as the first Decision Agent role
- checkpoint, permission, and gate behavior enforced by runtime policies

## Implementation Plan

The workflow adapter should land in phases that preserve clear ownership between schema, runtime, agents, and UI.

### Phase 1: Durable DAG Schema

- add workflow run schema with `nodes`
- add node state schema for `nodes/<id>.json`
- add decision schema for `decisions/*.json`
- add verification schema for implementation nodes
- add status enums and transition validation
- validate duplicate ids, missing dependencies, cycles, and invalid verification refs

Verification:

- schema tests cover valid workflow, invalid node refs, cycles, duplicate ids, invalid transitions, and invalid verification references
- parser tests prove non-DAG fixtures fail with clear schema errors

### Phase 2: Durable Run Materialization

- create unique run directories under `.opencode/harness/runs/<run>/workflow`
- materialize static templates into run directories
- write `workflow.json` and initial node files before scheduling
- add atomic JSON write helper with revision checks
- append basic `events.jsonl` records

Verification:

- tests create multiple workflows concurrently without path collision
- restart test reloads a materialized workflow and node files
- stale or missing node files place workflow into `needs_decision`

### Phase 3: DAG Executor

- compute ready nodes from DAG state
- schedule serial and parallel-ready nodes through runtime limits
- update node files for `ready`, `running`, and terminal states
- cancel or pause downstream nodes when required dependencies fail
- prevent completion while required test, review, or gate nodes are incomplete
- route failed verification nodes to deterministic retry or Decision Agent handling

Verification:

- integration tests cover linear DAG, parallel-ready nodes, downstream pause, and verification gates
- scheduler tests prove workflow DSL does not control concurrency

### Phase 4: Agent Routing

- define node type to capability routing table
- resolve requested agents only when allowed
- require `entry.delegable` for worker dispatch
- use `capability.purpose`, `capability.tags`, and `capability.writes` as routing signals
- record resolved agent and child session id in node files

Verification:

- routing tests choose implementation, research, review, and test agents by capability
- hidden or non-delegable agents are rejected
- permission mismatch blocks dispatch before execution

### Phase 5: Planner And Worker Contracts

- add Planner rules for workflow generation and required intent fields
- require implementation nodes that change behavior to include test/review/gate nodes or justify why verification is not required
- add Worker rules for node-only execution
- add Worker result protocol for `success`, `failed`, `blocked`, and `needs_replan`
- expose assigned node file paths to worker sessions

Verification:

- prompt snapshot tests include Workflow Runner rules
- worker prompt snapshots exclude workflow generation rules
- worker integration tests update only the assigned node file

### Phase 6: Runtime Runner Dispatch

- add explicit runner discriminator such as `runner: "chat" | "workflow" | "protocol"`
- map `workflow-runner` to the workflow runner
- expose `workflow.create`, `workflow.start`, `workflow.status`, `workflow.decide`, and `workflow.abort`
- require Workflow Runner to call `workflow.create` before direct execution tools for workflow-worthy tasks
- return workflow execution results to the model as `workflow.start` tool result
- keep worker execution on chat runner with node assignment prompt

Verification:

- session tests prove runner selection
- workflow tool tests prove create validates and persists without starting by default
- workflow tool tests prove start schedules execution and returns model-visible results
- worker invocation tests prove delegated workers do not receive workflow generation rules

### Phase 7: Decision Handling

- trigger decision request on unresolved `failed`, `blocked`, or `needs_replan`
- pass workflow, failed node, dependency nodes, artifacts, and events to Decision Agent
- validate bounded decision actions
- apply `retry_node`, `add_node`, `modify_node`, `request_input`, `replan_workflow`, and `abort_workflow`
- write validated decisions under `decisions/`

Verification:

- retry test increments attempt and returns node to `ready`
- add-node test updates DAG and materializes the new node file
- invalid decision leaves workflow in `needs_decision`
- abort decision cancels unscheduled downstream nodes

### Phase 8: UI And API

- expose workflow run/list/status endpoints
- return node statuses, blockers, artifacts, and decision-needed state
- expose resume and abort APIs
- show progress from runtime state, not model-written summaries

Verification:

- route tests cover create, status, resume, abort, and restarted runs
- UI tests show node progress and decision-needed state

## State Ownership Rule

Workflow durable state lives under the workflow run directory. Session state may hold references to the workflow run id, but node status, decisions, artifacts, and recovery records belong to the workflow adapter store.
