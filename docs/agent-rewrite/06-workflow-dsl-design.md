# Workflow DSL Design

## Purpose

Workflow DSL is the durable orchestration contract for multi-step agent work.

The workflow DSL should not try to predefine every possible workflow. It defines the structure, constraints, state files, and result protocol that let an orchestrator agent generate a task-specific workflow and let the runtime execute, resume, audit, and repair it.

The same format must support both:

- dynamic workflows generated by a Planner / Orchestrator agent
- static workflows written by humans for repeatable procedures

## Design Principles

- The workflow DSL describes orchestration state, not provider scheduling limits.
- The workflow file is a run record, not only a reusable template.
- The runtime owns validation, state transitions, scheduling, and permissions.
- The Planner owns workflow generation and later decision-making when execution cannot proceed deterministically.
- Workers own node execution only.
- Static and generated workflows must converge to the same durable run layout before execution.
- Every state change that matters for resume must be persisted before the next action starts.

## Terminology

- **Template**: a reusable workflow definition from package or user config.
- **Run**: a materialized workflow instance under `.opencode/workflows/<workflow_id>/`.
- **Workflow file**: the `workflow.json` run manifest and DAG.
- **Node file**: the durable assignment, progress, result, and error record for one DAG node.
- **Artifact**: any larger output referenced by path instead of embedded in JSON.
- **Decision**: a structured response from Planner / Decision Agent after a failure, block, or replan request.

## When To Generate A Workflow

Agents should not generate workflow DSL by default. Workflow generation is reserved for orchestration entrypoints.

Generate a workflow when at least one condition is true:

- the task has multiple dependent stages
- the task has independent subtasks that can run in parallel
- execution needs multiple agents or new sessions
- execution must survive process restart or session interruption
- failure handling needs retry, cancellation, added nodes, or replanning
- the user explicitly asks for orchestration, a long-running task, a plan that should execute, or progress tracking

Do not generate a workflow for:

- single-turn answers
- simple code explanations
- small current-session edits
- a single command
- worker execution of an already assigned node

Worker agents do not create workflows. They execute one assigned node and update that node's state file. If a worker cannot complete the node, it reports a structured status such as `blocked`, `failed`, or `needs_replan`.

## Roles

Agent role details are defined in `docs/agent-rewrite/08-workflow-runner-agent.md`.

### Planner / Orchestrator

The Planner is allowed to create the initial workflow and persist it before execution starts. It defines the DAG, node goals, dependencies, node types, success criteria, input references, and failure policies.

### Worker

The Worker executes exactly one node assignment. It reads the node file and referenced inputs, performs the task, writes progress, and finishes with a structured result.

The Worker should not know the full workflow generation rules. It only needs the node state protocol.

### Decision Agent

The Decision Agent handles exceptional execution states. In the first implementation, this can be the same agent as Planner. The runtime should still treat it as a separate role so a future Recovery agent can replace it without changing the workflow DSL.

The Decision Agent may choose one of a bounded set of actions:

- `retry_node`
- `skip_node`
- `cancel_branch`
- `add_node`
- `modify_node`
- `request_input`
- `replan_workflow`
- `abort_workflow`

## Runtime Responsibilities

The runtime is the enforcement layer. Agent rules are guidance; runtime checks are mandatory.

The runtime must:

- validate workflow files before execution
- persist workflow files before scheduling any node
- persist every node state transition
- schedule runnable DAG nodes based on dependencies
- decide actual parallelism from provider, model, and agent pool limits
- route nodes to suitable agents from node type and capability metadata
- restrict workers to updating their assigned node files
- restrict workflow mutation to Planner / Decision roles
- use atomic writes for state files
- append state changes to an event log when possible

Concurrency is not part of the workflow DSL. The DAG exposes which nodes may run together; the scheduler decides how many actually run.

## Planner Generation Contract

When a Planner generates a workflow, it must:

- decide that workflow mode is warranted using the generation criteria above
- create a unique run directory
- write `workflow.json`
- create one node file for every initial node
- validate DAG ids, dependency references, and cycles
- validate every node type against the supported enum
- persist all files before asking the runtime to execute

The Planner must include enough intent for later recovery:

- global goal
- assumptions
- success criteria
- per-node goal and task
- per-node success criteria
- dependency rationale when it is not obvious
- failure policy

The Planner should keep the first DAG as small as practical. It should not pre-expand speculative recovery branches. Failed or missing work can be added later through a Decision action.

## Worker Execution Contract

When a Worker receives a node assignment, it must:

- read the assigned node file
- read only referenced upstream node files and artifacts unless the task requires more context
- update progress in the assigned node file
- write artifacts under the workflow run `artifacts/` directory
- finish with one terminal node status or a decision-request status

The Worker must not:

- create a new workflow
- edit `workflow.json`
- edit another node's file
- change DAG dependencies
- silently continue after a blocker that invalidates the node goal

If the Worker believes the plan is wrong or incomplete, it should mark the node `needs_replan` and explain why in `error` or `signals`.

## Persistent Layout

Use a fixed workflow root, but never a fixed workflow instance directory. Every workflow run gets a unique directory.

Recommended project-local layout:

```txt
.opencode/workflows/
  wf_20260517_103012_a8f3/
    workflow.json
    lock
    events.jsonl
    nodes/
      research.json
      design.json
      implement.json
      test.json
    artifacts/
      research.md
      patch.diff
    decisions/
      failure_001.json
```

The workflow id should include a timestamp and random suffix to avoid collisions across sessions:

```txt
wf_YYYYMMDD_HHMMSS_<random>
```

Multiple sessions can safely create workflows under the same root as long as each workflow has its own directory. Concurrent updates to the same workflow must use a lock or atomic file writes.

## Workflow File

`workflow.json` is the stable DAG definition and run manifest. It should reference node files instead of embedding large progress or result payloads.

Recommended top-level fields:

| Field | Required | Owner | Notes |
|---|---:|---|---|
| `id` | yes | runtime | Unique workflow run id. |
| `schema` | yes | runtime | Integer schema version. |
| `goal` | yes | Planner | User-facing objective. |
| `status` | yes | runtime | Workflow status enum. |
| `created_at` | yes | runtime | ISO timestamp. |
| `updated_at` | yes | runtime | ISO timestamp. |
| `assumptions` | no | Planner | Planning assumptions useful for later decisions. |
| `success_criteria` | yes | Planner | Global completion criteria. |
| `nodes` | yes | Planner/runtime | DAG node references. |
| `policies` | no | Planner/runtime | Default failure and blocking behavior. |

Example:

```json
{
  "id": "wf_20260517_103012_a8f3",
  "schema": 1,
  "goal": "Fix SDK generation and verify the result.",
  "status": "running",
  "created_at": "2026-05-17T10:30:12Z",
  "updated_at": "2026-05-17T10:35:00Z",
  "assumptions": [
    "The JavaScript SDK is regenerated by packages/sdk/js/script/build.ts.",
    "Typecheck is the minimum verification gate."
  ],
  "success_criteria": [
    "The requested code change is implemented.",
    "The SDK is regenerated when API shapes changed.",
    "Relevant package typechecks pass."
  ],
  "nodes": [
    {
      "id": "research",
      "type": "research",
      "title": "Inspect SDK generation flow",
      "file": "nodes/research.json",
      "depends_on": []
    },
    {
      "id": "implement",
      "type": "implementation",
      "title": "Apply the code change",
      "file": "nodes/implement.json",
      "depends_on": ["research"]
    },
    {
      "id": "test",
      "type": "test",
      "title": "Verify the change",
      "file": "nodes/test.json",
      "depends_on": ["implement"]
    },
    {
      "id": "review",
      "type": "review",
      "title": "Review implementation and verification",
      "file": "nodes/review.json",
      "depends_on": ["test"]
    },
    {
      "id": "gate",
      "type": "gate",
      "title": "Accept workflow result",
      "file": "nodes/gate.json",
      "depends_on": ["review"]
    }
  ],
  "policies": {
    "on_node_failed": "ask_decision",
    "on_blocked": "ask_decision",
    "max_attempts": 2
  }
}
```

`workflow.json` should not contain provider concurrency settings.

Workflow node references should stay small:

| Field | Required | Notes |
|---|---:|---|
| `id` | yes | Stable node id unique within the workflow. |
| `type` | yes | Node type enum used for routing. |
| `title` | yes | Short display title. |
| `file` | yes | Relative path to the node file. |
| `depends_on` | yes | Node ids that must complete first. |
| `optional` | no | Whether downstream can proceed if this node is skipped. |

The runtime must reject duplicate ids, missing dependency targets, self-dependencies, and cycles.

## Node Types

Node type is a routing hint, not a hard-coded agent id. The runtime maps node type plus task content to an agent candidate using registry metadata.

Initial node type enum:

- `research`
- `planning`
- `design`
- `implementation`
- `debug`
- `test`
- `review`
- `gate`
- `documentation`
- `build`
- `release`
- `decision`
- `manual`

The mapping should be configurable. For example, `implementation` may route to a coding-capable agent, while `review` may route to a review agent. The workflow DSL should allow an optional requested agent, but the runtime should still resolve the final agent.

Routing should use this precedence:

1. explicit node `agent.requested`, if present and allowed
2. node type to capability mapping
3. agent registry `capability.tags` and `capability.purpose`
4. default delegable agent for the current model/provider

An agent is eligible only if its entry metadata allows delegation and its permission profile can satisfy the node's expected writes and tools.

## Verification And Gates

Implementation nodes should not silently absorb testing and review. The DSL should represent verification in two layers:

- node properties define required acceptance and verification gates
- dedicated `test`, `review`, or `gate` nodes execute those gates

This makes verification schedulable, retryable, auditable, and recoverable. It also lets the runtime distinguish:

- implementation completed but tests failed
- tests passed but review failed
- review passed but final gate needs a user or policy decision

Recommended pattern:

```txt
implement -> test -> review -> gate -> next
```

For broader changes:

```txt
             -> unit_test
implement -> typecheck -> review -> gate -> next
             -> integration_test
```

Implementation node example:

```json
{
  "id": "implement",
  "type": "implementation",
  "title": "Apply the code change",
  "file": "nodes/implement.json",
  "depends_on": ["research"],
  "verification": {
    "required": true,
    "strategy": "separate_nodes",
    "must_pass": ["test", "review"],
    "commands": ["bun typecheck"],
    "notes": [
      "Add or update focused tests for changed behavior.",
      "Do not mark implementation accepted until test and review nodes pass."
    ]
  }
}
```

Test node example:

```json
{
  "id": "test",
  "type": "test",
  "title": "Verify changed behavior",
  "file": "nodes/test.json",
  "depends_on": ["implement"],
  "success_criteria": [
    "Focused tests for changed behavior pass.",
    "Typecheck passes from the relevant package directory."
  ]
}
```

Review node example:

```json
{
  "id": "review",
  "type": "review",
  "title": "Review implementation and tests",
  "file": "nodes/review.json",
  "depends_on": ["test"],
  "success_criteria": [
    "Implementation satisfies the workflow goal.",
    "Tests cover the critical behavior and failure paths.",
    "No unrelated refactors or regressions are introduced."
  ]
}
```

Gate nodes are optional but useful when multiple verification branches must converge or when a user/policy decision is required before downstream work starts.

The runtime should treat `verification.must_pass` as an acceptance contract. A node with unmet required verification must not be considered accepted for workflow completion, even if its own execution status is `success`.

## Node File

Each node file is both the assignment and the durable execution record.

Recommended fields:

| Field | Required | Owner | Notes |
|---|---:|---|---|
| `id` | yes | runtime | Must match workflow node id. |
| `workflow_id` | yes | runtime | Parent workflow run id. |
| `schema` | yes | runtime | Node schema version. |
| `type` | yes | Planner | Node type enum. |
| `status` | yes | runtime/Worker | Node status enum. |
| `attempt` | yes | runtime | Starts at 0 or 1 and increments on retry. |
| `title` | yes | Planner | Short display title. |
| `task` | yes | Planner | Concrete task for the Worker. |
| `depends_on` | yes | Planner | Dependency ids copied from workflow for local readability. |
| `agent` | no | runtime | Requested and resolved agent/session data. |
| `input` | no | Planner/runtime | Referenced node files and artifacts. |
| `success_criteria` | yes | Planner | Node completion criteria. |
| `verification` | no | Planner/runtime | Required test/review/gate contract for this node's output. |
| `failure_policy` | no | Planner/runtime | Node-specific failure behavior. |
| `progress` | no | Worker | Mutable progress summary. |
| `result` | no | Worker | Structured success or partial result. |
| `error` | no | Worker/runtime | Structured failure or blocker. |
| `signals` | no | Worker | Hints for runtime or Decision Agent. |
| `artifacts` | no | Worker | Artifact references. |
| `created_at` | yes | runtime | ISO timestamp. |
| `started_at` | no | runtime | ISO timestamp. |
| `updated_at` | yes | runtime/Worker | ISO timestamp. |
| `finished_at` | no | runtime/Worker | ISO timestamp. |

Example while running:

```json

  "status": "running",

  ],

    "required": true,

      "Verification is executed by separate nodes, not swallowed by this implementation node."

    "on_failure": "ask_decision",
```

## Status Model

Workflow status:

- `created`
- `ready`
- `running`
- `success`
- `failed`
- `blocked`
- `cancelled`
- `needs_decision`
- `needs_replan`

Node status:

- `pending`
- `ready`
- `running`
- `success`
- `failed`
- `blocked`
- `skipped`
- `cancelled`
- `needs_decision`
- `needs_replan`

Only nodes whose dependencies have reached `success` or an allowed terminal state may become `ready`.

Allowed node transitions:

```txt
pending -> ready
ready -> running
running -> success
running -> failed
running -> blocked
running -> needs_decision
running -> needs_replan
failed -> ready
blocked -> ready
needs_decision -> ready
needs_replan -> ready
ready -> cancelled
pending -> cancelled
running -> cancelled
ready -> skipped
pending -> skipped
```

`failed`, `blocked`, `needs_decision`, and `needs_replan` are not always terminal. They pause scheduling for affected downstream nodes until deterministic policy or a Decision action resolves them.

Allowed workflow transitions:

```txt
created -> ready
ready -> running
running -> success
running -> failed
running -> blocked
running -> needs_decision
running -> needs_replan
running -> cancelled
needs_decision -> running
needs_replan -> running
blocked -> running
failed -> running
```

The runtime should reject stale transitions. For example, a Worker cannot write `success` after the runtime already cancelled the node.

## Failure Handling

The runtime should first apply deterministic policy:

- retry retryable errors within `max_attempts`
- skip nodes only when policy explicitly permits it
- cancel downstream nodes when a required dependency is cancelled or failed
- route failed `test`, `review`, or `gate` nodes to Decision Agent before accepting upstream implementation nodes
- block workflow completion while any required `verification.must_pass` node is not successful

When deterministic policy cannot decide, the runtime asks the Decision Agent. The Decision Agent reads:

- `workflow.json`
- the failed node file
- related upstream node files
- relevant artifacts
- `events.jsonl`

It then writes a decision file under `decisions/` and returns a bounded action. If the action changes the DAG, the runtime validates and persists the updated workflow before continuing.

Decision file example:

```json
{
  "id": "decision_001",
  "workflow_id": "wf_20260517_103012_a8f3",
  "node_id": "test",
  "created_at": "2026-05-17T10:42:00Z",
  "action": "add_node",
  "reason": "The test failed because generated SDK files were not refreshed after the implementation node.",
  "changes": {
    "nodes": [
      {
        "id": "regenerate_sdk",
        "type": "build",
        "title": "Regenerate JavaScript SDK",
        "file": "nodes/regenerate_sdk.json",
        "depends_on": ["implement"]
      }
    ],
    "replace_edges": [
      {
        "from": "implement",
        "to": "test",
        "with": ["regenerate_sdk", "test"]
      }
    ]
  }
}
```

Decision actions must be validated before mutation. Invalid decisions should leave the workflow paused in `needs_decision` with an error event.

## Event Log

`events.jsonl` is append-only. It is not the source of truth, but it makes debugging, audit, and replay easier.

Recommended event shape:

```json
{
  "time": "2026-05-17T10:35:00Z",
  "type": "node_status",
  "workflow_id": "wf_20260517_103012_a8f3",
  "node_id": "implement",
  "from": "ready",
  "to": "running",
  "actor": "runtime"
}
```

Useful event types:

- `workflow_created`
- `workflow_status`
- `node_created`
- `node_status`
- `node_progress`
- `artifact_written`
- `decision_requested`
- `decision_applied`
- `decision_rejected`
- `workflow_resumed`
- `workflow_cancelled`

## Persistence Rules

All JSON writes should use atomic replacement:

1. read current file
2. validate expected version or `updated_at`
3. write next content to a temporary file in the same directory
4. fsync when practical
5. rename over the old file
6. append an event

Each mutable file should include either a monotonically increasing `rev` or an `updated_at` timestamp that the writer checked before writing. `rev` is preferred for conflict detection.

Recommended ownership:

| File | Writers |
|---|---|
| `workflow.json` | runtime, Planner, Decision Agent through runtime validation |
| `nodes/<id>.json` | runtime and assigned Worker |
| `events.jsonl` | runtime |
| `decisions/*.json` | runtime after Decision Agent output validation |
| `artifacts/*` | assigned Worker or runtime |

Workers should submit node updates through runtime APIs when available. Direct file writes are acceptable only for early local implementation and must still obey ownership and atomic write rules.

## Resume Rules

On startup or resume, the runtime should:

1. discover workflow run directories
2. load and validate `workflow.json`
3. load every referenced node file
4. mark stale `running` nodes as `blocked` or `needs_decision` unless the owning session is still alive
5. recompute ready nodes from the DAG
6. continue scheduling only after all state files are consistent

If `workflow.json` references a missing node file, the workflow should enter `needs_decision`. If an unreferenced node file exists, the runtime should leave it untouched and record an audit event.

## Schema Boundaries

The workflow DSL should avoid becoming a programming language. Do not add arbitrary loops, general expressions, or unbounded code execution to workflow files.

Allowed control flow for the first DAG design:

- dependency edges
- optional nodes
- guard checks
- bounded retry policy
- Decision Agent mutations after runtime validation

Anything more complex should be represented by adding or modifying nodes through a Decision action, not by embedding a script language into the workflow DSL.

## Static Workflows

Static workflows should use the same schema. They can live under package or user config directories, but each run should still be copied or materialized into a unique durable run directory before execution.

Static definitions are templates. Runtime workflow directories are execution records.

## Compatibility With Current Implementation

The current MOD-13 implementation has sequential and branching workflows with `steps`, guards, error policy, checkpointing, and `dsl_context` state. This design is the next target shape:

- move from linear `steps` to DAG `nodes`
- split workflow definition from per-node durable state files
- route by node type and agent capability instead of fixed step agent id
- remove concurrency from the workflow DSL
- use Planner as the first Decision Agent implementation
- keep checkpoint and permission guard behavior as runtime policies
