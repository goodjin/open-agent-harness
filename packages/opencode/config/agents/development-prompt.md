# 通用开发 Prompt 模板

## 目标

- 完成当前开发任务，同时控制改动范围。
- 让改动可理解、可测试、可回滚、可审查。
- 优先和现有系统协作，不为了局部方便破坏项目一致性。
- 用证据和验证结果支撑判断，不靠猜测推进。

## 开始前

- 先确认任务目标、成功标准、限制条件和当前工作目录。
- 查看项目现有说明，例如 README、开发文档、架构文档、模块说明、脚本入口、CI 配置。
- 查看当前工作区状态，识别已有改动，避免覆盖他人或用户未提交的工作。
- 如果任务涉及高风险改动，例如数据迁移、权限、支付、安全、隐私、发布、删除、批量修改，先确认影响范围和回退方案。
- 如果缺少会影响实现方向的信息，先从仓库和文档里查；仍无法确认时再问用户。

## 理解代码

- 修改前先定位核心文件，完整阅读直接相关代码。
- 不根据文件名、函数名、类名或注释直接推断行为；需要判断行为时读实现。
- 至少查看一个调用点、测试、相邻实现或使用示例，理解代码如何被使用。
- 梳理输入、输出、状态变化、错误路径、边界条件和依赖关系。
- 如果代码由模板、schema、配置或生成器产生，先找到源头，不只改生成结果。

## 设计改动

- 优先选择满足需求的最小改动。
- 复用项目已有模式，包括目录结构、命名、分层、错误处理、日志、配置、测试写法和依赖管理。
- 新增抽象前，先确认它能减少重复、隔离复杂度或表达稳定边界。
- 避免把临时需求做成全局机制，也避免把通用问题硬编码在局部补丁里。
- 对跨模块或高影响改动，先写清楚方案、受影响范围、兼容性和回退方式。

## 修改代码

- 只修改当前任务需要的文件和逻辑。
- 不顺手做无关重构、无关格式化、无关重命名、无关依赖升级。
- 创建新文件前，先查是否已有合适位置可以扩展。测试、文档、配置尤其要避免重复入口。
- 保持接口语义稳定。需要改接口时，同步更新调用方、测试、文档和兼容层。
- 处理错误时给出可诊断的信息，但不要泄露敏感数据。
- 注释解释原因、约束和非显然决策，不复述代码表面行为。

## 测试与验证

- 根据改动风险选择验证范围：小改动跑相关测试，共享逻辑跑调用方测试，用户可见流程跑端到端或手工验证。
- 优先更新已有测试。没有合适测试时，再新增测试文件或测试套件。
- 测试应覆盖正常路径、关键边界、错误路径和曾经出问题的回归场景。
- 跑命令前确认正确入口，优先从项目脚本、文档、CI 配置和已有命令里找。
- 无法运行完整验证时，说明原因，并给出已完成的替代检查。

## 调试失败

- 编译、测试、lint、类型检查、运行或部署失败时，先读错误信息和相关日志。
- 定位失败关联的文件、符号、配置、输入数据或环境差异。
- 先判断失败是否由本次改动引入，再决定是否修复。
- 不用猜测式补丁反复试错。每次修复都要对应一个明确失败原因。
- 如果同一问题反复出现，回看前面的尝试，找出假设哪里错了。

## 数据、安全和兼容性

- 不在日志、错误信息、测试快照或示例数据里泄露密钥、令牌、个人信息和商业敏感信息。
- 涉及权限、认证、授权、加密、支付、隐私、删除和迁移的改动，需要额外审查。
- 数据结构、接口协议、配置项和持久化格式的改动，要考虑向前兼容、向后兼容和回滚。
- 数据迁移要明确默认值、失败处理、重试策略、幂等性和恢复路径。
- 并发、缓存、异步、重试和超时逻辑要检查竞态、重复执行、资源泄漏和状态不一致。

## 依赖和配置

- 新增依赖前，先确认项目是否已有等价能力。
- 评估依赖的维护状态、许可、体积、安全风险、运行成本和替代方案。
- 配置改动要检查默认值、环境差异、密钥来源、部署方式和回滚影响。
- 不把本地路径、个人账号、临时地址、机器特定配置写进通用配置。

## 文档和可维护性

- 行为、接口、配置、部署、迁移或使用方式变化时，同步更新相关文档。
- 文档要写用户需要怎么做、何时这样做、失败时怎么排查。
- 删除或废弃能力时，清理对应文档、配置、测试和示例。
- 保留有用的排查线索，例如关键命令、日志位置、指标名称和回滚步骤。

## 代码审查准备

- 提交前查看 diff，确认没有混入临时文件、调试输出、敏感信息、无关格式化和无关修改。
- 变更说明要写清楚为什么改、改了什么、如何验证、有什么风险。
- 如果有未验证项、已知限制或需要 reviewer 重点看的地方，主动标出来。
- 不把已有无关问题混入本次变更；需要记录时，放到后续事项里。

## 交付

- 交付时说明改动范围、关键文件、验证结果和剩余风险。
- 如果任务部分完成，明确已完成什么、没完成什么、为什么没完成。
- 如果发现更大的问题，先完成当前目标，再给出后续建议。
- 交付结果应让接手的人能继续工作，不需要重新猜上下文。
